## 项目名称

Moon JSON Repair（MoonBit 模块 `btlqql/moon_json_repair`，版本 0.1.0）

## GitHub 地址

https://github.com/btlqql/moon-json-repair

## 简介

纯 MoonBit 实现的保守 JSON 语法修复库。它对“近似 JSON”只做可审计的词法级修复：输出合法 JSON，保留未修改部分的原文拼写，并把每一次修改以原始 UTF-16 位置和稳定代码写入可回放的编辑日志。对无法可靠判断的输入（缺值、缺冒号、缺中间逗号、重复键、未结束字符串）直接拒绝，不猜测缺失的业务数据。另附 JSONL 批量诊断，以及一个仅用 Node 做 IO 的命令行。

## 方向与通用性

属于“数据与内容工具”方向的通用预处理基础库。它以库而非应用形态交付，不绑定任何业务模型、配置格式或日志格式；凡是需要先把不可信或半结构化文本收敛成合法 JSON 的 MoonBit 程序都可嵌入使用，因此能同时服务 AI 输出预处理、配置纠错、日志清洗等不同上层场景。

## 预期使用场景

1. **AI 结构化输出预处理**：上游模型返回 `{name:'Moon', enabled:true,}` 这类带单引号、裸键与尾逗号的文本。调用方调用 `repair` 得到合法 JSON 与编辑列表，先经 Schema 校验与权限检查再决定是否采纳；若返回 `Rejected("DUPLICATE_KEY")` 等稳定错误，则判定该次输出不可信并退回重试，而不是猜测字段。编辑列表同时可用于审计“模型输出被改动了什么”。
2. **人工配置文件纠错**：运维草稿配置里写了注释与尾逗号。用 `--report` 先预览修改记录，人工确认后再另存，程序默认不覆盖源文件；若报 `MISSING_VALUE`，说明确实写漏了，交回作者补全，而不是自动填入可能危险的默认值。
3. **JSONL 日志逐行检查**：数据管道对整批日志调用 `repair_jsonl`，逐行得到结果——成功给规范化输出，失败给错误码与行内偏移。管道据此隔离坏行、保留好行，既不因一条坏行中断整批，也不丢弃失败报告。

## 核心功能

裸键补引号（`QUOTE_KEY`）、单引号字符串转换（`SINGLE_QUOTE`）、行/块注释删除（`REMOVE_COMMENT`）、尾逗号删除（`TRAILING_COMMA`）；显式 opt-in 的容器闭合（`CLOSE_CONTAINER`）；UTF-16 原始位置编辑日志与 `apply_edits` 回放校验（拒绝越界、重叠与切断代理对）；`Options::conservative()` 与 `Options::strict()` 两档策略；JSONL 批量诊断；Node CLI（`--strict` / `--close-containers` / `--jsonl` / `--report`，退出码 0/1/2）。

## 技术路线

纯 MoonBit 递归下降解析，游标直接在原始 UTF-16 串上移动；修改只记入独立编辑日志，解析成功后由未改动切片与替换内容拼装输出，失败不返回部分结果。字符串与数字的词法合法性委托 MoonBit core 的 JSON 能力，不引入第三方依赖；对输入长度、递归深度、编辑数与行数设上限以约束资源。测试分三层：固定回归用例、确定性生成式不变量（幂等、严格重解析、输出必然合法）、以及用 Node 独立解析器交叉校验 CLI 输出。CI 在 wasm / wasm-gc / js / native 四后端执行格式化检查、构建、测试与示例运行。

## 明确不做的范围

不做完整 JSON5 兼容；不猜测缺失的中间值、冒号或逗号；不闭合未结束字符串；不剥离 Markdown 围栏；不转换 Python 字面量或 JSONP；不合并多个根文档；不做 JSON Schema 业务校验；不联网；不自动覆盖源文件。修复成功仅代表语法合法，不代表原始意图、Schema 或权限安全。

## 原创 / 参考来源与许可证

本项目为独立原创的 MoonBit 实现，许可证 Apache-2.0。行为边界的参考对象是 josdejong/jsonrepair（https://github.com/josdejong/jsonrepair ，ISC 许可证），仅作功能与设计对照，未导入其源码或测试夹具，也不声称与其兼容。语法依据 RFC 8259。查重时另核对到两个相邻项目：MBOpenClacky 内含一个用于工具参数的有界内部修复 helper（https://github.com/hnlyxiaobing/MBOpenClacky ，MIT 许可证），MoonParse 提供 JSON5 语法解析（https://github.com/caiklonghuan/MoonParse ，Apache-2.0 许可证）；前者是应用内的私有 helper，后者是容错解析，二者与本库“公开可复用 API + 可回放编辑日志 + 显式拒绝边界”的定位不同。

## 真实需求

工程实践中，模型输出、人工配置与运行日志三类来源大量产出“近似 JSON”而非严格 JSON。严格解析器会直接报错，让上层要么放弃整批数据、要么自行写难以维护的字符串替换；而常见的一次性修复脚本往往做全局替换，改了什么无法审计，还可能悄悄改变业务值。真正需要的是一个边界清晰、改动可见、无法确定时宁可不做的修复层。

## 生态差异

与容错解析器相比，本项目的差异不在“能接受多少语法”，而在“改动是否可审计、不确定时是否敢拒绝”：全部修改以原始位置记录并可回放校验，重复键（含转义后同名的键）一律拒绝以避免静默覆盖数据，缺失值一律不猜。与上游 jsonrepair 相比，本项目刻意选择更小的行为集合，不做 Markdown 围栏剥离、Python 字面量与多根合并，并以 MoonBit 原生库形态交付。因此我不宣称“生态中绝无同类”，而是说明定位与取舍的差异。

## 本人对方案的理解

我理解这个项目的核心不是“修复能力有多强”，而是把“修”与“不修”的边界画清楚并留下证据：修复动作必须可回放、可审计，无法可靠判断时必须明确拒绝并把问题交回上游。因此我把编辑日志与拒绝语义作为一等设计目标，而不是先追求覆盖率。容器闭合之所以默认关闭，是因为被截断的数字仍可能是完整 token，自动补全存在改变语义的风险。后续我会优先补强边界案例与文档，而不是盲目扩大可修复的语法集合。
